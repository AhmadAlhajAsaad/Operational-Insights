# FR-004: API Authenticatie en Autorisatie

**Status:** Draft
**Date:** 2026-02-16
**Author(s):** Backend Engineer Agent
**Related ADR:** [ADR-004-API-Authentication](../ADRs/ADR-004-api-authentication.md)
**Related TR:** [TR-001-Performance-Security-Standards](../Technical-Requirements/TR-001-Performance-Security-Standards.md)

## Doel

Het systeem moet de eigen API endpoints beveiligen zodat alleen geauthenticeerde en geautoriseerde Equans medewerkers toegang hebben tot de data. Dit voorkomt ongeautoriseerde toegang tot gevoelige Atlassian en GitHub data.

---

## User Stories

### US-1: Inloggen met Equans Credentials

**As a** Equans medewerker
**I want to** inloggen met mijn bestaande Equans account (Microsoft/Azure AD)
**So that** ik geen apart account hoef aan te maken voor dit systeem

### US-2: Automatische Sessie Verlenging

**As a** ingelogde gebruiker
**I want to** mijn sessie automatisch verlengd zien worden
**So that** ik niet steeds opnieuw hoef in te loggen tijdens mijn werkdag

### US-3: Veilig Uitloggen

**As a** gebruiker
**I want to** kunnen uitloggen
**So that** anderen op mijn computer geen toegang hebben tot mijn sessie

### US-4: Toegang Geweigerd Melding

**As a** gebruiker zonder juiste rechten
**I want to** een duidelijke melding zien wanneer ik geen toegang heb
**So that** ik weet dat ik contact moet opnemen met een beheerder

### US-5: Rol-Gebaseerde Toegang

**As a** System Administrator
**I want to** verschillende toegangsniveaus kunnen toekennen aan gebruikers
**So that** gevoelige data alleen beschikbaar is voor geautoriseerde personen

## Functionele Requirements

### FR-004.1: Azure AD Authenticatie

**Beschrijving:** Gebruikers authenticeren via Azure AD (Entra ID) met hun Equans credentials.

**Acceptatiecriteria:**

- [ ] Gebruikers kunnen inloggen met hun Equans Microsoft account
- [ ] Single Sign-On (SSO) werkt als gebruiker al ingelogd is in Microsoft 365
- [ ] Multi-Factor Authentication (MFA) wordt ondersteund indien geconfigureerd in Azure AD
- [ ] Login flow volgt Microsoft security best practices

---

### FR-004.2: JWT Token Validatie

**Beschrijving:** Elke API request wordt gevalideerd op basis van een geldig JWT token.

**Acceptatiecriteria:**

- [ ] Requests zonder token krijgen HTTP 401 Unauthorized response
- [ ] Requests met ongeldig/verlopen token krijgen HTTP 401 Unauthorized response
- [ ] Geldige tokens worden geaccepteerd en request wordt verwerkt
- [ ] Token validatie gebeurt bij elke API request

---

### FR-004.3: Beveiligde Endpoints

**Beschrijving:** Alle API endpoints met gevoelige data zijn beveiligd.

| Endpoint Pattern       | Beveiliging   | Beschrijving                     |
| ---------------------- | ------------- | -------------------------------- |
| `GET /health`          | Publiek       | Health check (geen auth vereist) |
| `GET /api/atlassian/*` | Authenticated | Atlassian data endpoints         |
| `GET /api/github/*`    | Authenticated | GitHub data endpoints            |
| `GET /api/admin/*`     | Admin Role    | Administratie endpoints          |

**Acceptatiecriteria:**

- [ ] `/health` endpoint is publiek toegankelijk voor monitoring
- [ ] Alle `/api/*` endpoints vereisen geldige authenticatie
- [ ] Admin endpoints vereisen specifieke Azure AD groep membership

---

### FR-004.4: Rol-Gebaseerde Autorisatie (RBAC)

**Beschrijving:** Toegang tot bepaalde functies is gebaseerd op Azure AD groepen/rollen.

| Rol    | Beschrijving        | Toegang                                |
| ------ | ------------------- | -------------------------------------- |
| Viewer | Standaard gebruiker | Alleen lezen van dashboards            |
| Admin  | Beheerder           | Lezen + force refresh + admin functies |

**Acceptatiecriteria:**

- [ ] Rollen worden bepaald op basis van Azure AD groep membership
- [ ] Viewers kunnen data bekijken maar niet verversen
- [ ] Admins kunnen `force_refresh=true` gebruiken
- [ ] Ongeautoriseerde acties resulteren in HTTP 403 Forbidden

---

### FR-004.5: Token Refresh

**Beschrijving:** Tokens worden automatisch ververst zonder gebruikersinteractie.

**Acceptatiecriteria:**

- [ ] Access tokens worden automatisch ververst vóór expiratie
- [ ] Refresh gebeurt op de achtergrond zonder gebruikersinteractie
- [ ] Bij gefaalde refresh wordt gebruiker naar login gestuurd
- [ ] Maximale sessieduur is configureerbaar (standaard: 8 uur)

---

### FR-004.6: Veilig Uitloggen

**Beschrijving:** Gebruikers kunnen hun sessie beëindigen.

**Acceptatiecriteria:**

- [ ] Logout knop is beschikbaar in de UI
- [ ] Na logout worden alle tokens verwijderd uit geheugen
- [ ] Na logout wordt gebruiker naar login pagina gestuurd
- [ ] Oude tokens werken niet meer na logout

---

### FR-004.7: Error Handling

**Beschrijving:** Authenticatie fouten worden duidelijk gecommuniceerd.

| Situatie       | HTTP Status | User Message                        |
| -------------- | ----------- | ----------------------------------- |
| Geen token     | 401         | "Inloggen vereist"                  |
| Verlopen token | 401         | "Sessie verlopen, opnieuw inloggen" |
| Ongeldig token | 401         | "Authenticatie mislukt"             |
| Geen toegang   | 403         | "Geen toegang tot deze functie"     |

**Acceptatiecriteria:**

- [ ] Frontend toont gebruiksvriendelijke foutmeldingen
- [ ] Technische details worden niet getoond aan eindgebruikers
- [ ] Bij 401 wordt gebruiker automatisch naar login gestuurd
- [ ] Bij 403 wordt duidelijke melding getoond met contactinformatie

## Gebruikers Scenario's

### Scenario 1: Eerste Login

```
Gebruiker opent de applicatie
→ Systeem detecteert geen geldige sessie
→ Gebruiker wordt doorgestuurd naar Azure AD login
→ Gebruiker voert Equans credentials in (+ MFA indien vereist)
→ Azure AD redirect terug naar applicatie met tokens
→ Frontend slaat tokens op in geheugen
→ Dashboard wordt geladen met geauthenticeerde API calls
```

### Scenario 2: API Request met Geldige Token

```
Frontend maakt request naar GET /api/atlassian/users
→ Authorization header bevat: "Bearer <jwt_token>"
→ Backend valideert JWT (signature, expiry, audience)
→ Token is geldig
→ Backend haalt user identity uit token claims
→ Backend checkt of user geautoriseerd is voor endpoint
→ Data wordt geretourneerd
```

### Scenario 3: Verlopen Token

```
Frontend maakt request met verlopen token
→ Backend valideert JWT
→ Token is verlopen (exp claim in verleden)
→ Backend retourneert 401 Unauthorized
→ Frontend detecteert 401 response
→ MSAL library probeert token refresh
→ Refresh succesvol: request wordt opnieuw gedaan
→ Refresh mislukt: gebruiker naar login pagina
```

### Scenario 4: Ongeautoriseerde Actie (Admin Only)

```
Viewer gebruiker probeert force_refresh te gebruiken
→ Frontend stuurt request met force_refresh=true
→ Backend valideert JWT (geldig)
→ Backend checkt user roles uit token
→ User heeft geen Admin rol
→ Backend retourneert 403 Forbidden
→ Frontend toont: "Je hebt geen rechten voor deze actie"
```

### Scenario 5: Logout

```
Gebruiker klikt op "Uitloggen"
→ Frontend roept MSAL logout aan
→ Tokens worden verwijderd uit geheugen
→ Azure AD logout wordt aangeroepen
→ Gebruiker wordt doorgestuurd naar login pagina
→ Volgende API calls falen met 401
```

- Network toegang tot Azure AD endpoints
